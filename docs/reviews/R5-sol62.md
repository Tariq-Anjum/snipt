# Snipt R5 — NOT READY

Reviewed the seven S15 commits and the R4 fixes through `e854582`. In-memory probes reproduced a v4 upgrade failure, restore flags applied to the wrong messages, and SMS provider state diverging during send hand-off. The S15 review also found two ways to lose a valid MMS and a path that bypasses the native image size check. I made no file changes. Later working-tree edits were outside the pinned review.

## Blockers

1. **High · v4 can prevent a valid database from opening.** Archive a conversation whose ID is `2^40 + 1`, then delete its last message. The thread summary is removed, but the archive flag remains. When v4 moves a surviving archived conversation from `2^40 + 2` into that ID, the flag update fails. The in-memory probe ran the migration’s SQL and reproduced `UNIQUE constraint failed: archived_threads.thread_id`. The transaction rolled back to v3. With an unarchived survivor, the same probe showed it inheriting the orphan flag. A separate message-renumbering probe made a retired `mms_pending.msg_id` resolve to an unrelated message. **Fix:** account for reference-only IDs when planning the remap, clear or detach orphan references, and invalidate stale notification identities when allocator ranges are recycled. [Migration destinations](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/ids.rs:125) · [Reference updates](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/ids.rs:138) · [Empty-thread cleanup](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/threads.rs:248)

2. **High · Restoring your own backup can archive the wrong thread and complete the wrong reminder.** Export follows insertion order. Restore matches identical rows in ID order without reserving exact matches. The SQLite probe inserted two matching rows in reverse ID order and restored their own archive. Both mappings were swapped, so the existing archive and completion flags ended up on both rows. **Fix:** reserve exact identity matches across the whole archive before matching the remaining duplicates. Use thread affinity where available and reject ambiguous flag mappings. [Export ordering](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/query.rs:127) · [Candidate selection](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/restore.rs:142) · [Flag writes](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/restore.rs:274)

3. **High · Android delete can remove the OUTBOX row during a live send.** After binding and before `endSend`, the UI can delete the provider row before the core refuses to delete the local message. The two-store probe applied that ordering and left the attempt bound to a missing row. Later reconciliation can remove the local copy too. A second race is in initialization: Tauri and JNI can both pass the `OnceLock` check before publication. The later initializer can run recovery after the first has opened a live attempt. The recovery SQL probe confirmed that this closes the live guard. **Fix:** reserve deletion against send start and binding before any provider write, and put opening plus recovery inside a single serialized initializer. [Provider-first delete](/mnt/MD/AI-tools/mySMS/src-tauri/src/commands/mod.rs:175) · [Store guard](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/threads.rs:225) · [Send hand-off](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/SmsSender.kt:77) · [Shared initialization](/mnt/MD/AI-tools/mySMS/src-tauri/src/core.rs:72)

4. **High · SMS replay can still resurrect a deleted message.** The receiver writes the provider row before local ingest. An import can identify it as missing in that gap. If the receiver then ingests it and local cleanup deletes it before replay writes, the replay inserts it again despite the new tombstone. The SQLite probe reproduced eligibility, tombstone creation, and reinsertion under the production predicates. **Fix:** check the tombstone inside the same store transaction that inserts a replayed row. [Receiver ordering](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/SmsDeliverReceiver.kt:45) · [Import and replay](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/ProviderSync.kt:166) · [Ingest lookup](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/ingest.rs:235)

5. **High · MMS maintenance can discard a successful final attempt.** A repeated WAP push starts attempt three, increments the counter, and immediately invokes maintenance. The SQLite probe confirmed the exhausted query selects that still-running attempt. Maintenance writes a terminal placeholder, and the later success callback rejects the PDU. There is a second consistency window: the callback releases `inFlight` before parsing and writes the provider row before core ingest. A competing callback or ingest failure can leave a provider row without a matching Snipt message. **Fix:** claim completion per attempt, keep that claim through the provider and store writes, and finalize a placeholder only after failure or timeout. Give each attempt its own URI and make provider writes recoverable across a rejected commit or restart. [WAP ordering](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/MmsWapPushReceiver.kt:26) · [Exhaustion query](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/mms.rs:240) · [Callback ordering](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/MmsDownloader.kt:124) · [Terminal-state check](/mnt/MD/AI-tools/mySMS/src-tauri/src/core/mms.rs:188)

6. **High · MMS transaction IDs are treated as globally unique forever.** The production insert and schema collapsed two notices with identical transaction IDs and different subscriptions and locations into one row in SQLite. If the first row is terminal, the second MMS is ignored. If it is pending, the WAP path can submit the first location on the second subscription. OMA scopes the ID to the notification and response exchange. **Fix:** scope deduplication to the subscription and retrieval identity, bound completed deduplication records, and use the subscription from the claimed row for the download. [Unique key](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/schema.rs:169) · [Notice lookup](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/mms.rs:152) · [Download routing](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/MmsWapPushReceiver.kt:66) · [OMA MMS Encapsulation §6.2](https://www.openmobilealliance.org/release/MMS/V1_3-20110913-A/OMA-TS-MMS_ENC-V1_3-20110913-A.pdf)

7. **High · The WebView bypasses the thumbnailer’s pixel cap.** The native thumbnailer rejects rasters above 40 MP, but the store has already accepted the original by signature and encoded byte size. `mms_image(..., true)` returns the original when a thumbnail is missing, and the thread automatically renders it. The full viewer also requests the original. The cached core test explicitly confirms original-byte fallback. A bounds probe confirmed that a 100 MP raster rejected by native policy can still reach both WebView paths. A full RGBA decode at those dimensions would require about 400 MB. Actual WebView memory behavior was unverified. **Fix:** persist display eligibility after dimension validation, enforce it on both IPC modes, and refresh the UI when a real thumbnail arrives. [Native bounds](/mnt/MD/AI-tools/mySMS/plugins/tauri-plugin-telephony/android/src/main/java/app/snipt/telephony/MmsDownloader.kt:188) · [Store fallback](/mnt/MD/AI-tools/mySMS/crates/sms-store/src/mms.rs:403) · [Automatic thumbnail request](/mnt/MD/AI-tools/mySMS/src/components/MmsAttachments.tsx:88)
